## 一、并发安全的作用（为什么需要这套测试）

### 1.1 并发场景的风险

系统上线后会同时服务多个用户，进程内存在**大量共享状态**：

```
共享状态                       并发风险
─────────────────────────────────────────────────
登录限流表 _login_fails/_login_ip   计数错乱 → 误锁 / 防爆破失效
embedding LRU 缓存 _embed_cache    缓存竞争 → 丢命中 / 数据损坏
提示词库锁 prompt_store._lock      并发写 → 丢更新 / 覆盖
会话/消息归属（SQLAlchemy Session） 并发写 → 串号 / 脏读
审计写入（crisis_audit）           并发触发 → 归属错乱 / 丢审计
```

三种典型并发故障：
- **不丢更新**：并发创建 5 条数据，最终只剩 3 条（丢更新）；
- **不串号**：A 的请求结果落到 B 的会话/列表里（串号——最危险的隐私事故）；
- **不损坏**：并发写同一资源，内容被截断/半覆盖/归属校验被绕开。

### 1.2 为什么心理系统必须过并发测试

并发下"串号"意味着**一个用户的私密心理对话可能出现在另一个用户的视野**——这是数据隔离在时间维度的延伸：隔离不仅要在单请求下成立，还要在**多用户同时操作**时成立。

### 1.3 测试方法：mock 的定位

- **真实逻辑**：登录校验、会话/提示词/审计的归属过滤、数据库读写全部走真实代码；
- **mock 对象**：仅替换 embedding API 与 LLM 调用（固定向量 + 固定回答），使并发问答**完全本地化、稳定可复现**（不依赖外部网络与费用），同时仍走完整的「安全检测 → 检索 → 生成 → 持久化」链路。

## 二、测试用例（18 项断言）

| 分组 | 用例 | 并发方式 | 验证点 |
|---|---|---|---|
| **A. 并发登录** | 8 用户同时登录，各自 token 调 `/api/auth/me` | 8 线程 | token 与账号一一对应（不串号） |
| **B. 并发创建会话** | A/B 各并发建 5 个会话 | 16 线程 | 总数不丢（各 5）、列表零交集 |

| **F. 数据库层** | 并发后按 user 计数 | — | 与预期一致、无跨用户行 |

## 五、结论

1. **并发安全验证通过**：登录、创建、提示词写入、越权防护、问答、审计在 8~16 线程并发下**不丢更新、不串号、不损坏**；
2. 关键结论：
   - 并发登录 token 一一对应（登录状态不串）；
   - 并发创建无丢失（计数精确）且列表零交集（归属不串）；
   - 并发问答后**会话消息只含自己的问题**（隐私不串）；
   - 并发越权写入全部 403（归属校验并发下不破）；
3. 说明系统当前的进程内共享状态（登录限流表、embedding 缓存、提示词库锁、SQLAlchemy 会话）在单进程并发下安全。

## 六、遗留建议

| 项 | 建议 |
|---|---|
| 多进程部署 | 登录限流 / embedding LRU / 提示词库锁均为**进程内**；多 worker 部署时必须改为共享存储（Redis 限流、共享 embedding 缓存或独立推理服务），否则并发结论仅适用于单进程 |
| 数据库连接池 | PostgreSQL 连接池（SQLAlchemy pool）在多并发下建议压测连接上限，避免连接耗尽 |
| 读写混合压测 | 当前为功能级并发；建议用 `scripts/concurrency_test.py` 做持续读写压测（含安全路径问题池），观察响应时间与错误率 |
| 审计并发 | E 用例验证了归属不串，建议补充"同一用户并发触发危机拦截"场景，验证审计逐条写入不丢 |
