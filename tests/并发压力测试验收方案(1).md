# rag-psychology 并发压力测试验收方案

> 文档性质：并发改造完成后的发布验收标准  
> 适用架构：单实例、单 Uvicorn worker、进程内并发调度、PostgreSQL/pgvector、无 Redis  
> 候选参数：`max_active=20`、`max_queue=40`、`queue_timeout=30s`  
> 核心原则：HTTP 200 不等于业务成功；必须同时证明上限受控、排队正确、异常可回收、数据不串号、性能达标。

---

## 1. 验收结论口径

本轮测试解决的不是“FastAPI 能否同时收到请求”，而是以下五个问题：

1. 任意时刻实际执行昂贵链路的请求是否始终不超过 20 个。
2. 第 21～60 个请求是否进入有界 FIFO 队列，而不是在线程池、数据库或模型供应商处隐式堆积。
3. 第 61 个及之后的请求是否快速、明确地被拒绝。
4. 完成、失败、超时、取消和客户端断线后，槽位与用户占位是否全部释放。
5. 在真实 RAG、危机检测、持久化和 SSE 全部开启时，用户体验与资源消耗是否达到发布门槛。

最终结论只能为以下三种之一：

| 结论 | 定义 |
|---|---|
| 通过 | 所有 P0 一票否决项为 0，全部必测场景通过，量化指标连续 3 轮达标 |
| 有条件通过 | 仅非核心观测项存在偏差，已有负责人、整改期限和明确降级参数；不得包含任何 P0 问题 |
| 不通过 | 任一 P0 问题出现，或关键性能指标未达标，或测试证据不完整 |

## 2. 事实边界与测试前置条件

### 2.1 已确认事实

- 当前目标方案不使用 Redis，只承诺单实例、单 worker 内的并发上限。
- 同步接口和 SSE 接口必须共用同一个准入控制器及同一组 20 个活跃槽位。
- 等待队列最多容纳 40 个请求，排队超过 30 秒必须进入明确终态。
- PostgreSQL/pgvector 是本次并发发布证据所使用的数据层；SQLite 只能用于本地冒烟。

### 2.2 最新代码审计发现

本节以 GitHub `main` 的 `fd976ec2`（`4.2并发初版`）为基线。该版本已经实现服务端 Ticket、进程内 FIFO 队列、20 个活跃槽位、40 个等待位、排队超时、单用户单请求、取消接口以及同步/SSE 统一准入。因此，准入模块已进入“需要严格验证实现边界”的阶段，不再属于“尚未实现”。

当前仍需由本方案重点验证的风险包括：

- 多 worker 守卫只检查 `WEB_CONCURRENCY`；必须验证通过 Uvicorn `--workers` 参数启动时也会被阻断。
- 运行中取消需要证明真正终止上游生成；不能只设置 `cancelling` 标志后仍生成完整答案。
- SSE 排队期间发生传输层断连或任务取消时，必须立即移除队列项，不能只依赖一秒轮询或最终 `release()`。
- 后台持久化在响应返回后执行；必须验证任务失败、队列积压和服务关闭时不会静默丢失会话或危机审计。
- 现有压测脚本仍需区分 SSE `done` 与 `error`，并补充 TTFT、排队时间、request_id 和业务终态统计，才能作为正式验收工具。

### 2.3 开始压测前必须满足

以下任一项不满足，禁止开始正式压力测试：

- 服务端已经实现统一 `AdmissionController`，同步与 SSE 均在昂贵链路前准入。
- 可以读取 `active`、`queued`、`max_active`、`max_queue` 等状态或等价指标。
- 所有终态都在 `finally` 或等价可靠清理逻辑中释放资源。
- 启动配置明确为 1 个实例、1 个 worker；检测到多 worker 时应阻断启动或产生阻断级告警。
- 压测客户端能够完成真实注册/登录并携带 Bearer Token。
- SSE 客户端能区分 `done` 与 `error`；收到 `error` 不得记为成功。
- 每个请求均有唯一 `request_id`，客户端和服务端日志可以关联。
- 测试环境、代码提交号、模型名称、数据库连接池参数和机器配置已经冻结并记录。
- 不读取或打印 `.env` 内容；测试参数通过测试进程环境、CI Secret 或运维注入提供。

## 3. 固定测试环境

### 3.1 生产等价拓扑

| 项目 | 固定要求 |
|---|---|
| API | 1 个实例 × 1 个 Uvicorn worker |
| 准入后端 | 进程内 `asyncio` 调度器，无 Redis |
| 并发参数 | active 20、queue 40、queue timeout 30 秒 |
| 关系数据库 | PostgreSQL，独立测试库 |
| 向量数据库 | pgvector，使用固定知识库快照 |
| 接口 | `/api/query` 与 `/api/query/stream` |
| 业务开关 | 真实业务验收时 RAG、危机检测、重排、持久化和长期记忆按生产配置开启 |
| 反向代理 | 与生产一致；若生产无反向代理则直连 Uvicorn |
| 网络 | 压测机与服务机分离；记录基础 RTT、丢包率和带宽 |

测试期间不得临时增加 worker、关闭安全检测、关闭持久化或缩短回答内容来换取漂亮数据。

### 3.2 两类模型链路

| 链路 | 用途 | 是否能单独作为发布依据 |
|---|---|---|
| 可控 Mock LLM/embedding | 验证准入状态机、FIFO、取消、超时和故障回收 | 否 |
| 真实模型 API | 验证真实 TTFT、完整响应时间、供应商限流和费用 | 是 |

Mock 必须支持固定延迟、逐 token 输出、永久挂起、连接失败、429、500 和中途断流。Mock 测试通过只说明调度正确，不说明真实用户体验达标。

## 4. 指标定义

### 4.1 业务结果

| 指标 | 定义 |
|---|---|
| 业务成功 | 同步接口返回完整合法响应；SSE 严格收到 `done`，且答案、来源和终态字段合法 |
| 业务失败 | 5xx、超时、连接异常、SSE `error`、流未正常结束、响应结构错误或答案为空 |
| 正确拒绝 | 达到 active+queue 上限后按契约返回 429 + `AI_QUEUE_FULL` + `Retry-After` |
| 成功率 | 业务成功数 ÷ 已被准入且未由测试主动取消的请求数 |
| 契约正确率 | 返回结果与该场景预期状态完全一致的请求数 ÷ 总请求数 |

正确拒绝属于背压成功，不计入业务失败；但返回码、错误码、响应时间或拒绝数量不正确时，属于契约失败。

### 4.2 时延

| 指标 | 起止点 |
|---|---|
| `queue_wait_ms` | 服务端接收 Ticket 至获得活跃槽位 |
| `ttft_ms` | 客户端发出请求至收到第一个有效 token |
| `run_ms` | 获得槽位至业务链路实际退出 |
| `total_ms` | 客户端发出请求至收到完整终态 |

必须报告 P50、P95、P99 和最大值。平均值只能辅助观察，不能代替分位数。

### 4.3 系统指标

- `active`、`queued`、各终态计数、拒绝原因计数。
- API CPU、RSS 内存、事件循环延迟、线程池使用量。
- PostgreSQL 活跃连接、连接等待、慢查询、锁等待。
- pgvector 查询时延、重排耗时、embedding 与 LLM 请求量。
- 上游 429、5xx、连接错误、read timeout 和实际重试次数。
- SSE 当前连接数、客户端断开数和上游流关闭数。

## 5. 准入边界测试

以下测试先使用“每个请求固定执行 5 秒”的可控 Mock，所有请求通过 barrier 在 1 秒内同步起跑。每个请求使用独立用户，单用户重复提交场景除外。

| ID | 输入 | 预期结果 | 量化通过条件 |
|---|---|---|---|
| G-01 | 20 个请求 | 全部立即运行 | `active` 峰值恰为 20；`queued=0`；20 个均成功 |
| G-02 | 21 个请求 | 20 个运行，1 个排队 | `active≤20`；队列峰值恰为 1；释放后队首运行 |
| G-03 | 60 个请求 | 20 个运行，40 个排队 | `active` 峰值 20；`queued` 峰值 40；无拒绝 |
| G-04 | 61 个请求 | 20 运行、40 排队、1 拒绝 | 恰好 1 个 429；拒绝响应 P95≤1 秒 |
| G-05 | 80 个请求 | 20 运行、40 排队、20 拒绝 | 恰好 20 个 429；契约正确率 100% |
| G-06 | 同一用户同时提交 10 个请求 | 仅 1 个获得未完成请求资格 | 1 个被接受，其余 9 个均为 409 `AI_REQUEST_IN_PROGRESS` |
| G-07 | 10 个同步 + 10 个 SSE，再追加 5 个混合请求 | 前 20 个共享槽位，后 5 个排队 | 总 `active≤20`，不得出现“同步20 + SSE20” |
| G-08 | 分别以 `WEB_CONCURRENCY=2` 和 Uvicorn `--workers 2` 启动 memory 后端 | 两种方式均应阻断启动 | 不允许出现两个各自拥有 20 个槽位的进程 |

监控端每 50 毫秒采样一次状态。任何一个采样点出现 `active>20` 或 `queued>40`，整轮直接判定失败。

## 6. FIFO、公平性与排队超时

| ID | 场景 | 量化通过条件 |
|---|---|---|
| Q-01 | 20 个槽位占满后，按 Q1～Q20 顺序加入队列 | 未取消请求的启动顺序与入队顺序 100% 一致 |
| Q-02 | 队列中间随机取消 20% | 被取消项不再执行；其余请求保持 FIFO；无跳过、重复或幽灵运行 |
| Q-03 | 让活跃请求持续超过 30 秒 | 所有排队项在 30±1 秒进入 `TIMEOUT`；不得调用 RAG/LLM |
| Q-04 | 恰在超时边界释放一个槽位 | 每个 Ticket 只能进入一个终态；不得同时出现 STARTED 和 TIMEOUT |
| Q-05 | 混合 `persist=true/false`、同步和 SSE | 全部进入同一个 FIFO 口径，不因接口或持久化选项插队 |

队列位置展示允许因网络传播产生短暂误差，但服务端实际启动顺序必须严格符合 FIFO。

## 7. 取消、断线与异常释放

每个故障场景均先占满 20 个槽位，并至少排队 5 个正常请求；故障请求退出后应自动提升队首。

| ID | 故障注入 | 量化通过条件 |
|---|---|---|
| R-01 | 正常完成 | 退出后 1 秒内 `active` 减 1，队首开始运行 |
| R-02 | LLM 返回 500 | 请求进入 FAILED；退出后 1 秒内释放槽位 |
| R-03 | LLM 返回 429 | 遵守有限重试策略；不得无限占槽；最终释放 |
| R-04 | embedding/read timeout | 在配置 deadline 内结束；不得留下后台任务 |
| R-05 | SSE 客户端收到部分 token 后断开 | 3 秒内观察到上游流关闭；不得把半截答案作为正常完成结果落库 |
| R-06 | 同步客户端断开 | 服务端按约定取消或等待底层真实退出；底层未退出前不得提前释放造成超卖 |
| R-07 | 排队请求取消 | 1 秒内从队列移除并释放用户占位；不得调用模型 |
| R-08 | 持久化失败 | 回答按产品契约结束；无论是否返回答案都必须释放槽位并记录错误 |
| R-09 | cancel 与 release 同时发生 1000 次 | 每次只有一个有效状态迁移；最终 `active=0`、`queued=0` |
| R-10 | SSE 正在排队时直接关闭 TCP/取消 ASGI 任务 | 1 秒内从队列移除；不得被后续 `_promote()` 提升为无人消费的活跃请求 |

所有场景结束后统一等待 5 秒并断言：

```text
active = 0
queued = 0
unfinished_user_claims = 0
orphan_async_tasks = 0
database_connections = 测试前基线 ± 1
```

任一数值不归零即判定资源泄漏。

## 8. 数据隔离与业务正确性

使用至少 40 个独立用户，每个问题包含不可重复标记，执行 20 个同步请求与 20 个 SSE 请求混合并发。

通过条件：

- 会话、消息、来源、长期记忆和危机审计跨用户串号数量为 0。
- 每个成功请求恰好产生约定数量的消息记录，不多写、不少写、不重复写。
- 被取消、排队超时和队满拒绝的请求不得写入正常问答记录。
- 高危问题全部走正确安全路径；普通问题不得因并发串入他人的安全等级或来源。
- 同一会话发生受支持的并发操作时，消息顺序符合产品约定且数据库无完整性错误。

后台持久化还必须单独验证：

- `done` 后立即读取会话时，产品契约必须明确是“已经落库”还是“最终一致”；实现和文案不得互相矛盾。
- 后台队列积压达到上限时，回退路径不丢数据，且延迟突增有指标和告警。
- 强制让数据库写入失败，客户端即使已经收到成功回答，也必须产生可检索的失败指标与补偿记录。
- 服务优雅关闭时应先停止接收新任务并排空队列；待处理任务丢失数量必须为 0。
- 危机审计属于关键数据，不得仅依靠内存队列实现“尽力而为”保存。

任何跨用户数据泄漏均为 P0，整轮测试立即停止。

## 9. 压力与容量测试模型

### 9.1 测试组合

| 类型 | 并发/流量 | 时长或次数 | 目的 |
|---|---|---|---|
| Mock 阶梯 | 1、5、10、20、40、60、80 | 每档 5 分钟 | 找本地服务与准入边界 |
| 同步起跑 | 20、21、60、61、80 | 每档连续 10 轮 | 精确验证槽位、队列和拒绝数量 |
| 混合流量 | 50% SSE、30%同步问答、20%健康/查询接口 | 30 分钟 | 模拟真实接口竞争 |
| 尖峰 | 1 秒内从 0 增加到 80 个请求 | 10 轮 | 验证背压与恢复 |
| 稳态耐久 | 持续维持 15～20 个活跃问答 | 2 小时 | 检测内存、连接和槽位泄漏 |
| 真实模型阶梯 | 1、5、10、20；20 并发至少 100 个请求 | 每档至少 10 分钟 | 验证真实体验和供应商容量 |

真实模型测试达到费用预算或停止条件后应停止，不得为了得到更高并发数字无控制地继续消耗额度。

### 9.2 目标性能门槛

以下门槛以生产等价环境、真实模型、业务开关全开为准：

| 同时到达请求数 | 预期准入行为 | 业务成功率 | SSE TTFT P95 | 完整响应 P95 | 队列等待 P95 |
|---:|---|---:|---:|---:|---:|
| 5 | 全部立即运行 | ≥99.5% | ≤1.5 秒 | ≤7 秒 | ≤0.2 秒 |
| 20 | 全部立即运行 | ≥99.0% | ≤2 秒 | ≤8 秒 | ≤0.5 秒 |
| 40 | 20 运行、20 排队 | ≥98.0% | ≤7 秒 | ≤13 秒 | ≤6 秒 |
| 60 | 20 运行、40 排队 | ≥98.0% | ≤12 秒 | ≤20 秒 | ≤12 秒 |
| 80 | 60 个准入、20 个拒绝 | 准入请求≥98.0%；拒绝契约100% | 对准入请求≤12 秒 | 对准入请求≤20 秒 | ≤12 秒 |

说明：40/60/80 档的 TTFT 和完整响应时间包含排队时间。若真实模型单轮时长明显变化，应先重新测量单请求基线，再经产品评审调整门槛，不得测试后私自放宽。

### 9.3 系统健康门槛

| 指标 | 通过条件 |
|---|---|
| 活跃请求峰值 | 始终 ≤20 |
| 等待队列峰值 | 始终 ≤40 |
| `/api/health` | 满载时 P95≤200ms，P99≤500ms，成功率 100% |
| 事件循环延迟 | P95≤100ms，P99≤250ms |
| CPU | 2 小时稳态平均≤70%，连续 1 分钟不得超过 90% |
| 内存 | 预热后 2 小时增长≤10%，且不得呈持续线性增长 |
| PostgreSQL | 无连接获取超时；峰值不超过配置的 pool+overflow 总预算 |
| 数据库错误 | deadlock、连接泄漏、事务状态错误均为 0 |
| 上游错误 | 目标 20 并发下，LLM 429+5xx+timeout 合计≤1% |
| 服务端异常 | 未捕获异常、进程退出、事件循环卡死均为 0 |

### 9.4 耐久测试门槛

2 小时稳态结束后必须同时满足：

- 业务成功率 ≥99.5%。
- active、queued、用户占位和异步任务全部回到 0。
- RSS 内存相对预热完成时增长 ≤10%。
- 数据库连接回到基线 ±1，无持续增长。
- P95 与第一个 15 分钟窗口相比劣化不超过 20%。
- 无需重启服务即可继续通过 G-01、G-04 两个边界测试。

## 10. 一票否决项

出现以下任一情况，直接判定并发压力测试不通过：

1. 任意时刻 `active>20` 或 `queued>40`。
2. 同步与 SSE 分别占用独立额度，导致总活跃数超过 20。
3. 队满请求没有在 1 秒内明确拒绝，而是继续隐式等待。
4. SSE `error`、空答案或半截答案被统计为成功。
5. 取消、断线、超时或异常后存在槽位、用户占位、数据库连接或异步任务泄漏。
6. 出现任何跨用户会话、消息、来源、记忆或危机审计串号。
7. 为通过压测临时关闭 RAG、安全检测、持久化或其他生产功能。
8. 使用多 worker 跑进程内调度，却仍宣称全局上限为 20。
9. 压测工具未鉴权、未真实读取完整 SSE、未记录业务终态或统计口径无法复核。
10. 测试环境、代码提交号或原始结果文件缺失，导致报告不可重复。
11. 后台持久化任务在数据库故障或服务关闭时静默丢失，尤其是危机审计数据丢失。

## 11. 执行顺序

必须按以下顺序执行，前一阶段失败不得继续用更大流量掩盖问题：

1. AdmissionController 状态机单元测试。
2. API 状态码与 SSE 事件契约测试。
3. 20/21/60/61/80 精确边界测试。
4. 取消、断线、超时、429、500、数据库失败等故障注入。
5. 40 用户数据隔离与持久化回归。

## 13. Definition of Done

只有同时满足以下条件，才能对外表述“通过并发压力测试”：

1. 所有 P0 一票否决项数量为 0。
2. 20/21/60/61/80 边界行为和拒绝数量完全符合预期。

5. 40 用户混合并发数据串号为 0。
6. 20 并发真实模型链路达到成功率、TTFT 和完整响应门槛。
