## 一、为什么要做真实链路压测（与 Mock 压测的区别）

| 维度 | 测试点 4：性能压测（Mock） | 测试点 5：真实链路压测 |
|---|---|---|
| embedding / LLM | 替身（固定向量/回答） | **真实调用** |
| 测的是什么 | 系统自身上限（本地处理能力） | **端到端**表现（含模型时延与 QPS 限制） |
| 单请求时延 | ~40ms | **4~18s+**（LLM 思考链 + 生成为主） |
| 吞吐上限决定者 | 本地 CPU / 连接池 | **模型提供方并发生成能力** |
| 费用 | 0 | 按 token 计费（思考模式输出翻倍，费用更高） |
| 意义 | 本地处理能在多大并发下扛住 | 真实用户并发下的端到端体验与吞吐边界 |

Mock 压测回答了「系统自己最多能扛多少」；真实链路压测回答「**真实环境下用户能获得怎样的体验、吞吐被谁卡住**」。

---

## 二、测试方法

### 2.1 方案

- 阶梯并发 **1 / 5 / 10 / 20 / 50 / 100 / 150**（共 7 档，覆盖体验区→压力区→极限区），每级持续 8s；
- 三个接口：`/api/system-prompt`（纯 DB 读对照）、`/api/query`（同步完整 RAG）、`/api/query/stream`（SSE 流式，测 TTFT）；
- **所有模型开启思考模式**：同步接口内部经同步流式（`llm_stream.stream`）实现，与流式接口共用同一思考参数；
- 用户池 10 个独立账号轮换；压测后自动清理账号与数据。

### 2.2 运行

```bash
# 全谱系思考模式压测（1→150，约 500+ 次真实生成，注意费用）
python tests/test_performance.py --live --levels 1,5,10,20,50,100,150 --duration 8

# 输出 JSON 报告
python tests/test_performance.py --live --report tests/results/performance-live-thinking.json
```

### 3.2 思考模式 vs 非思考模式对比（本次重测的关键）

| 并发 | 同步 query avg（思考→非思考） | 流式完整 avg（思考→非思考） | RPS（思考→非思考） |
|---|---|---|---|
| 1 | 4629 → 3006ms | 4183 → 9146ms | 0.2 → 0.4 |
| 10 | 4591 → 2799ms | 4354 → 6950ms | 2.9 → 3.9 |
| 20 | 4691 → 2887ms | 5234 → 8255ms | 5.2 → 7.6 |
| 50 | 7196 → 3665ms | 9867 → 10172ms | 9.9 → 16.6 |
| 100 | 12583 → 7023ms | 15841 → 10425ms | 12.5 → 21.8 |
| 150 | 18385 → 9909ms | 28579 → 17819ms | 18.8 → 28.5 |

**关键结论：**
1. **同步/流式时延终于一致**（低并发下同步 4.6-4.7s ≈ 流式 4.2-5.2s）——思考模式统一生效，消除了之前"流式比同步慢 3 倍"的配置不一致；
2. **思考模式的成本**：单请求从 ~2.8s → ~4.6s（**+65%**），吞吐全面下降约 **40%**（模型输出 token 翻倍：思考链 + 回答）；
3. **高并发劣化更重**：150 并发同步 P99 25.0s、流式 P99 **31.5s**；流式 TTFT 150 并发 10.5s（思考链也在排队生成）；
4. **本地接口次瓶颈提前**：150 并发 system-prompt P99 8.4s（长请求占满事件循环更久）。

## 四、结论与容量规划（思考模式）

```
体验区  1-20 并发    同步/流式 4.2-5.2s、TTFT <460ms   ✅ 可用
压力区  50 并发      P99 10.6-11.3s                   ⚠️ 开始不可接受
极限区  100 并发     P99 17.4-17.4s                   ❌ 延迟不可接受
崩坏区  150 并发     P99 25-31.5s、吞吐平台期          ❌ 仅探边界
```

| 目标 | 结论 |
|---|---|
| **单进程部署上限** | **20 并发**（P99 < 6s）；超过后用户体验崩坏（思考模式比非思考低 2.5 倍） |
| **吞吐上限** | ~19 RPS（150 并发后平台期；非思考模式为 ~28） |
| **要支持 50+ 并发** | 需多 worker 部署 + Redis 共享状态，或评估关闭思考模式 |
| **思考模式的取舍** | 回答质量更高（有推理链）但成本 +65%、吞吐 -40%；若前端不展示思考链，建议评估是否值得 |

## 五、遗留建议

| 项 | 建议 |
|---|---|
| 思考模式配置 | 已统一：同步/流式均 `enable_thinking=True`（同步内部经同步流式实现）；若想关闭，`.env` 设 `ENABLE_THINKING=false` 即可回退（同步走 `llm.invoke`） |
| 前端展示思考链 | 若保留思考模式，建议前端流式展示思考过程（提升可解释性），否则思考内容白生成 |
| 费用测算 | 思考模式每次问答约生成 1500-2500 tokens（非思考 ~500-1500），成本约翻倍，按此估算压测与运营成本 |
| 容量规划 | 思考模式下目标 P99<6s → 单进程上限 20 并发；50+ 需多 worker + Redis（见测试点 3 遗留项） |
| 真实压测自动化 | 建议 CI 低频运行（费用敏感）；Mock 压测（测试点 4）用于日常回归 |
