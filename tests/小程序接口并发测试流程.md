## 1. 并发设计

### 1.1 四类接口的代价分级

| 接口 | 链路 | 是否走准入（20 槽位/40 队列） | 主要代价 | 并发关注点 |
|---|---|---|---|---|
| `/api/mp/register` | 建镜像号 + 档案 upsert | **否** | DB 写（users + family_profile + children） | 幂等、并发建号不冲突、不产生重复行、不 5xx |
| `/api/mp/update` | 档案 upsert | **否** | DB 写 | 并发 upsert 不报错、不丢更新、不改坏他人档案 |
| `/api/mp/query` | 安全检测 + RAG + LLM + 落库 | **是** | **昂贵**（LLM 秒级） | 准入、排队、TTFT、成功率、数据隔离 |
| `/api/mp/query/stream` | 同上（SSE） | **是** | **昂贵** | 准入 + SSE 终态（done/error）+ 断线回收 |

**设计含义**：两个写接口不占槽位，但会消耗 DB 连接池；只有两个 query 接口会真正排队、被拒绝。所以两组要分别压——写接口看「零失败」，query 看「成功率 + TTFT/Total 门槛」。

### 1.2 三个必须写进设计的约束

**① 单用户单请求 → userId 池必须 ≥ 并发数（最关键）**

mp 通道沿用了 Web 端的准入语义：同一 `userId` 同时只能有 1 个在途请求，第二个立即返回 `409 AI_REQUEST_IN_PROGRESS`。
这与 JWT 版压测脚本「每请求新建一个账号」的做法**完全不同**——如果并发 20 却只用 5 个 userId，你测到的将是一堆 409，而不是真实吞吐。

> 脚本默认建 `max(并发×2, 50)` 个 userId 并循环取用，确保同一时刻不会有重复 userId 在途。用 `--users` 可覆盖。
> 例外：两个写接口**不走准入**，所以 `--users 1`（全部并发打同一 userId）是合法且必要的压法，见 §4 的 W-02。

**② mp 与 Web 共用同一组 20 个槽位**

`api/mp.py` 直接 `from modules.concurrency.service import admission`——**不是**独立配额。
所以小程序流量会**直接挤占 H5/Web 流量**，两者加起来 `active ≤ 20`、`queued ≤ 40`。压测期间若同时有人用 H5，观察到的 `active` 会混入对方流量。

**③ 同一 userId 复用同一 sessionId → 天然形成长会话**

脚本中每个用户的 `sessionId` 固定为 `sess_<userId>`，所以压测 10 分钟下来单用户会累积几十轮，短期窗口（6 轮）会持续滚动。
这既更贴近真实，也顺带压了「长会话 + 安全检测对窗口内全部 human 轮次检测」的开销；缺点是不同轮次间有上下文耦合，属预期。

### 1.3 指标与门槛

| 指标 | c1 / c5 | c10 / c20 |
|---|---|---|
| 业务成功率 | ≥ 99.5% | ≥ 99% |
| TTFT P95 | ≤ 1500ms | ≤ 2000ms |
| 完整响应 P95 | ≤ 7000ms | ≤ 8000ms |
| **写接口模式（writes）成功率** | **100%**（fail=0、rejected=0） | 同 |
| `active` 峰值 | ≤ `max_active`(20) | 同 |
| `queued` 峰值 | ≤ `max_queue`(40) | 同 |
| 跨用户串号 | **0** | **0** |
| 结束后 5s 内 | `active=0` 且 `queued=0` | 同 |

**口径**：`409/429/503` 属**正确拒绝（背压成功）**，不计入失败，但会单独统计——如果真实模型下 409 大量出现，说明 userId 池不够或单用户在途时间过长，属于压测配置问题，不算服务失败。
（注：两个写接口模式下不存在合理拒绝，任何 409/429/503 都算失败。）

### 1.4 一票否决项

1. `active > 20` 或 `queued > 40`（任一采样点）。
2. 任一跨用户串号（A 的回答里出现 B 的孩子昵称）。
3. 出现非 503 的 5xx。
4. 结束后 `active`/`queued` 未归零（槽位泄漏）。
5. 写接口模式（`--endpoint writes`）出现任何失败/拒绝（幂等或并发 upsert 有问题）。
6. 为跑通而临时关闭 RAG / 安全检测 / 持久化 / 长期记忆 / 档案注入。

## 4. 正式执行（窗口 B，按序执行）

> **W 先跑，W 不过不要往下跑。**
> 窗口 B 的**工作目录固定为 `tests\`**：下面命令里的 `..\scripts\` 和 `results\` 都相对它，报告会落在 `tests\results\`。

### W · 写接口并发安全（register + update，不消耗额度，约 3 分钟）

| # | 命令 | 验证点 |
|---|---|---|
| W-01 | `python ..\scripts\mp_concurrency_test.py --endpoint writes --output results\mp-writes-c20.json steady --concurrency 20 --duration 60` | 两个写接口混合，成功率 100%、0 个 5xx |
| W-02 | `python ..\scripts\mp_concurrency_test.py --endpoint writes --users 1 --output results\mp-writes-same-user.json steady --concurrency 20 --duration 60` | 同 userId 并发 upsert：幂等、无主键冲突、不 5xx |

> W-02 的 `--users 1` 让 20 个并发**全打同一个 userId**——这是专门压「并发建号 + 档案整份 upsert 幂等」的。写接口不走准入，所以不会撞 409。
> 这一项曾真的抓到过缺陷：`upsert_family_profile` 旧实现是「SELECT 判空 → INSERT」，并发下两处 TOCTOU 窗口分别撞 `user_family_profile_pkey` 与 `user_children_pkey`（约 7% 请求 500）。已改为 `INSERT ... ON CONFLICT DO UPDATE`，实测 400/400 通过。

### Q · query / stream 单接口专项（各 3 分钟，看清楚每个接口单独的形态）

```cmd
python ..\scripts\mp_concurrency_test.py --endpoint query  --output results\mp-only-query-c20.json  steady --concurrency 20 --duration 180
python ..\scripts\mp_concurrency_test.py --endpoint stream --output results\mp-only-stream-c20.json steady --concurrency 20 --duration 180
```
预期：两者**单独**跑时都能跑满 20 槽位；`stream` 的 TTFT 明显低于 total，`query` 的 TTFT≈total（非流式没有首字概念）。

### C · 正式 4 档 · 真实模型稳态阶梯（主体，约 5 分钟）

> 与网页端《真实模型阶梯手动执行流程》§4 **一一对应**：同样的 c1/c5/c10/c20 四档、同样的 50% SSE 混合比（`--sse-ratio 0.5`）、同样的时长主导（`--total 0`）、同样的判定门槛。
> **两处差异**：
> ① **时长按 60 秒/档**（上游模型 API 额度有限，压不起 10 分钟/档；网页端文档仍写 600）。四档连跑约 5 分钟。代价是样本量小，解读注意事项见下方 ⚠️。
> ② Web 脚本把门槛写死在 `automatic_thresholds()` 里，所以网页端命令行短；**mp 脚本不按档位自动套门槛**，必须显式传 `--min-success/--max-ttft-p95/--max-total-p95`，否则 TTFT/Total 默认 0 = 不校验（漏测）。故下面四条比网页端多三个参数，其余完全对齐。

```cmd
REM ---- c1：1 并发 ----
python ..\scripts\mp_concurrency_test.py --endpoint mixed --sse-ratio 0.5 --min-success 99.5 --max-ttft-p95 1500 --max-total-p95 7000 --output results\mp-real-c1.json steady --concurrency 1 --duration 60 --total 0

REM ---- c5：5 并发 ----
python ..\scripts\mp_concurrency_test.py --endpoint mixed --sse-ratio 0.5 --min-success 99.5 --max-ttft-p95 1500 --max-total-p95 7000 --output results\mp-real-c5.json steady --concurrency 5 --duration 60 --total 0

REM ---- c10：10 并发 ----
python ..\scripts\mp_concurrency_test.py --endpoint mixed --sse-ratio 0.5 --min-success 99.0 --max-ttft-p95 2000 --max-total-p95 8000 --output results\mp-real-c10.json steady --concurrency 10 --duration 60 --total 0

REM ---- c20：20 并发（60 秒 × 20 并发 ≈ 350~400 请求）----
python ..\scripts\mp_concurrency_test.py --endpoint mixed --sse-ratio 0.5 --min-success 99.0 --max-ttft-p95 2000 --max-total-p95 8000 --output results\mp-real-c20.json steady --concurrency 20 --duration 60 --total 0
```

> - 每档末尾打印 `最终结论：通过 / 不通过` + FAIL 项清单；完整报告 JSON 在 `results\mp-real-cX.json`。
> - 判定门槛与网页端 §5（= 方案 §9.2）同口径，来源见本文 §1.3：
>   c1/c5 → TTFT P95 ≤ 1500ms、Total P95 ≤ 7000ms、成功率 ≥ 99.5%；c10/c20 → 2000ms / 8000ms / ≥ 99%。
> - ⚠️ **60 秒档样本量偏小，解读要克制**。按实测频率（每用户约 30 次/分钟，即 `60 ÷ 单请求平均耗时`，与并发数无关），单档请求数约为：c1 ≈ 30、c5 ≈ 150、c10 ≈ 280、c20 ≈ 350~400。由此：
>   - **c1/c5 的 P95 实际就是「最大值」附近**（30 个样本时 P95 落在第 29 个值上），TTFT/Total 门槛会随单次波动随机通过或失败；
>   - c1/c5 的成功率门槛在 60 秒下**等价于「零失败」**（150 个样本出现 1 个失败 = 99.33% < 99.5%）；
>   - 结论：60 秒档适合**回归/守线**（抓明显劣化、抓上游 429、抓串号与槽位泄漏），**不要拿它下「P95 刚好达标 / 差一点」这种精细结论**。需要把门槛当硬指标时，把该档单独加长到 `--duration 600` 重跑一次即可（其余参数不动）。

## 5. 结果判读

脚本末尾会打印：
```
请求数 / 成功 / 失败 / 拒绝
成功率    串号
TTFT  P50/P95/P99
Total P50/P95/P99
准入峰值 active=x/20  queued=y/40
  - 每个接口的 total/ok/fail/rej/rate/status 分布
最终结论：通过 / 不通过
  FAIL: ...
```
完整 JSON 在 `--output` 指定路径，含 `endpoints`（分接口明细）、`overall`、`admission`（峰值）、`isolation_violations`（串号详情）、`drain_final`（结束时状态）、`verdict`。

**常见判读**

| 现象 | 含义 | 处理 |
|---|---|---|
| **429 占绝大多数，且 `active_peak=0`** | **不是队列满**，而是全局限流中间件在拦（漏设 `RATE_LIMIT_TIMES`） | 回 §3.1 重启服务。可实测阈值：并发打 2300 次 `GET /api/mp/profile`，若恰好 2000 个 200 后全 429 即默认值 2000 |
| **日志大量上游 `429 limit_requests`**（URL 是 `maas.aliyuncs.com/.../chat/completions`），且 `[admission] wait_ms=0` 全为 0 | **上游模型 RPM 额度不足**，非服务缺陷。非流式路径表现为 **500**（`api/mp.py` 把所有异常统一转 500，会误触发「非 503 的 5xx」一票否决）；流式路径表现为 SSE `error` 终态（脚本计 fail）。SDK 重试还会把在途时间拉长 → 连带出现更多 409 | 到百炼控制台确认/申请该模型的 RPM 额度；或降档（c20 → c10）找上游稳定点；结论记为**「模型侧容量」**而非并发不达标 |
| 429 少量出现（query/stream） | 队列已满（active 20 + queue 40） | 属**正确拒绝**，确认 `Retry-After` 与契约正确即可 |
| **`status=0` 与 5xx 数量近似 1:1** | 500 的连带伤：服务端异常后关闭连接，复用该连接的请求报 `RemoteProtocolError` | 按 5xx 去修，别当两个独立问题查 |
| 409 占比很高 | userId 池 < 并发数，或单轮耗时过长导致同用户在途 | 加大 `--users`；这是压测配置问题，不是服务失败 |
| 503 出现 | 排队超 30s | 真实模型下说明并发远超容量，降低档位 |
| 仅 TTFT/Total 超线，成功率达标 | 模型性能门槛问题 | 保留 JSON，交产品评审（同 Web 通道 §5 的处理口径） |
| 串号 > 0 | **P0**，立即停止 | 保留 JSON 与服务端日志，查 `user_chat_history` 与 profile 注入的 user_id 过滤 |
| 结束未归零 | 槽位泄漏 | 查是否有 SSE 断线未回收 |

## 7. 常见问题速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 全部 401 | `MP_API_KEY` 非空但脚本没带 | 加 `--api-key <值>`，或 `set MP_API_KEY=<值>`（脚本不读 `.env`） |
| **启动报「检测到已有实例（PID xxxx）」但 8000 连不上** | **僵尸锁 + PID 复用**：上次实例被强杀/崩溃，锁文件残留；该 PID 已被系统回收给别的进程（实测遇到过被 QQPCTray 复用），`_pid_alive` 误判为存活 | 先确认 8000 确实无监听，再删锁文件重启动：<br>`python -c "import os,tempfile;os.remove(os.path.join(tempfile.gettempdir(),'rag_psychology_memory_8000.lock'))"` |
| 启动报已有实例且 8000 确实在监听 | 真有实例在跑 | 用那个实例即可，不要重复启动（memory 准入只允许单实例）；想并行验证可换 `set PORT=8001` |
| 写接口档出现 500 | 档案 upsert 的唯一键竞态（`UniqueViolation` on `user_family_profile_pkey` / `user_children_pkey`） | 看服务端日志确认；`db/crud_async.upsert_family_profile` 应使用 `INSERT ... ON CONFLICT DO UPDATE`（2026-09-10 已修） |
| `chat 403 Free quota exhausted` | 仍免费额度 | 回 §2.1 |
| 服务端刷 `memory 落库失败: 403` | embedding key/额度 | 查 `EMBEDDING_API_KEY`（§2.3 的 embed 行） |
| 换模型后行为未变 | 改了 `.env` 或代码没重启 | Ctrl+C 重启服务 |

## 附：脚本参数速查

| 参数 | 说明 |
|---|---|
| `--endpoint` | `query`（仅 /api/mp/query）/ `stream`（仅 /query/stream）/ `mixed`（默认，按 `--sse-ratio` 混合两者）/ `writes`（仅 register+update）。脚本另保留 `crud`（含 profile）与 `all`，本流程不使用 |
| `--sse-ratio` | `mixed` 中流式占比，默认 0.5 |
| `--users` | userId 池大小；不传（或传 0）时自动取 `max(并发×2, 50)`；**显式值原样生效**——`--users 1` 即让全部并发打同一个 userId（仅 `writes`/`crud` 适用；非写接口模式会大量 409，脚本会打印告警） |
| `--min-success` / `--max-ttft-p95` / `--max-total-p95` | 判定门槛，0 = 不校验；写接口模式不看这三个，直接要求 fail=0 |
| `--reuse-question` | 不追加唯一标记（会命中 embedding 缓存，仅缓存专项用） |
| `--api-key` | 与 `.env` 的 `MP_API_KEY` 一致；不传则读环境变量 |
| 子命令 | `steady --concurrency N --duration S [--total T]`（本流程只用这个）；`boundary` / `spike` 仍在脚本里但本流程不使用 |
