## 一、为什么必须做备份与恢复测试

### 1.1 两个必须明确的运维指标

| 指标 | 含义 | 本次实测 |
|---|---|---|
| **RPO**（Recovery Point Objective） | 灾难发生后最多丢多少数据（= 备份频率） | 备份完成后新写入的数据全部丢失（符合预期，丢多少取决于备份间隔） |
| **RTO**（Recovery Time Objective） | 从灾难发生到恢复服务需要多久 | **完整 RTO 1.5s**（数据恢复 0.4s + 服务重启 0.7s，1.7 MB 全库） |

### 1.2 为什么"恢复演练"比"有备份"更重要

- 备份文件存在 ≠ 能恢复：文件损坏、恢复命令不对、扩展缺失、owner 不匹配——全是线上事故源；
- **没演练过的备份流程，在真出事故时第一次执行 = 高风险操作**；
- 本项目刚完成 PostgreSQL 迁移，**此前没有任何备份机制**——本次先建立备份能力（`scripts/backup_pg.py`），再演练完整恢复闭环。

## 二、备份机制（`scripts/backup_pg.py`）

```bash
python scripts/backup_pg.py              # 全量备份到 backups/（pg_dump 自定义格式）
python scripts/backup_pg.py --keep 7     # 仅保留最近 7 份
```

- **全库导出**：关系表 + pgvector 向量表在同一库，`pg_dump -F c` 天然全覆盖（8 张表）；
- **行数快照**：每个 dump 附带 `.snapshot.json`（8 张表行数），供恢复后一致性核对与监控；
- **定时备份**（Windows）：任务计划程序 → 每天执行一次上述命令即可（已写入脚本 docstring）。

### 手动恢复命令（灾难场景）

```bash
pg_restore -h 127.0.0.1 -U postgres -d rag_psychology --no-owner backups/rag_psychology_<时间戳>.dump
```

## 三、演练流程（5 步闭环）

```
1. 取最近备份（dump + 行数快照）
2. 备份后写入 3 个 RPO 标记用户（rpo_*）——模拟"备份完成后又有新数据"
3. 故意破坏：DROP 全部 8 张表（含 pgvector 向量表）
4. 从 dump 恢复（计时 → RTO）
5. 核对：8 张表行数 vs 备份快照必须完全一致；RPO 数据必须丢失；init_db 幂等 + 管理员可用
```

### 4.2 RPO / RTO（完整口径）

```text
[RPO] 备份后写入的 3 个用户已丢失（未混入恢复数据）→ 符合预期 ✓
[数据恢复] pg_restore 回放 dump → 0.4s
[服务重启] uvicorn 启动至 /api/health 200 → 0.7s
[完整 RTO] 数据恢复 + 服务重启 = 1.5s（备份 1.7 MB）✓
[应用] init_db 幂等 + 管理员账号存在 → 服务可直接提供问答 ✓
```

> RTO 口径说明：0.4s 仅是「数据恢复」环节耗时；完整 RTO（灾难发生 → 服务恢复可用）
> 还包含服务重启与健康检查，实测 **1.5s**。真实灾难场景下需另加：发现/告警、人工决策、
> 定位备份等时间（未计入）。

### 4.3 演练中的插曲（同样有价值的发现）

首次演练暴露 2 个脚本问题并已修复：
1. `users` 表 `updated_at` NOT NULL——原生 SQL 插入需显式提供（SQLAlchemy 默认值不生效）；
2. 删库后 `COUNT(*)` 对不存在表抛 `UndefinedTable` 且**事务未回滚**导致后续查询全被拒（`InFailedSqlTransaction`）——已加回滚容错。

## 五、结论与运维建议

1. **备份能力已建立**：`scripts/backup_pg.py` 一键全量备份（1.7 MB / 秒级），附行数快照；
2. **恢复闭环验证通过**：删库→恢复→逐表一致（8/8），**完整 RTO 1.5s**（数据恢复 0.4s + 服务重启 0.7s），应用直接可用；
3. **RPO 语义确认**：备份完成后新写入的数据会丢——**RPO 取决于备份频率**（每天备份 = 最多丢 1 天数据；要求更高的环境应缩短备份间隔或启用 WAL 归档/PITR）。

| 建议 | 说明 |
|---|---|
| 定时备份 | 任务计划程序每天执行 `backup_pg.py`；生产环境建议每日全量 + 定期 PITR（时间点恢复） |
| 演练频率 | 建议每季度演练一次恢复（验证备份文件仍可恢复、流程无人为依赖） |
| RPO 目标 | 若业务要求丢数 <1 天 → 保持日备；若需分钟级 → 启用 WAL 归档（pg_wal + pg_basebackup） |
| 备份异地 | 备份文件与数据库同机，建议定期拷贝到异机/对象存储 |
