## 一、数据隔离的作用（为什么需要这套机制）

### 1.1 与「鉴权与越权」的分工

鉴权与越权解决的是**权限边界**：谁能访问、谁不能访问（无 token → 401、A 访问 B 的资源 → 403）。
数据隔离解决的是**数据边界**：即使攻击者拿到了**合法身份**，也读不到、改不了、删不掉**别人的数据**。

```
鉴权与越权：     身份是否有效（401） + 权限是否越界（403）
数据隔离：       「数据在谁名下」永不混淆 —— 我写入的，只属于我
```

### 1.2 为什么内容级断言比状态码断言更强

- 状态码 403 只能说明「接口拒绝了」，无法证明「内容没泄露」；
- 数据隔离测试的关键手段：给 A 的数据打上**唯一私有标记**（`PRIV_A_xxx`），断言 **B 的任何响应文本中都不出现该标记**——即使未来某个接口忘了返回 403，只要 B 的响应里混入了 A 的标记，测试立即判定为泄露（防「半隔离」）。

### 1.3 心理数据隔离的严肃性

本系统存储青少年心理健康对话记录与危机干预审计（高危敏感数据）：

- 会话消息泄露 → 未成年人隐私外泄，可能造成二次伤害；
- 提示词内容泄露 → 业务 Prompt 策略（含危机话术）外泄；
- 危机审计被跨用户读取 → 合规留痕失效；
- 因此「A 写入的数据 B 查不到」是本系统的**硬性安全需求**。

### 1.4 四层隔离防线（对应测试断言）

| 防线 | 验证内容 | 断言 |
|---|---|---|
| ① 接口层 | B 用 A 的 session_id / prompt_id / compare_id 操作（读/改/删/激活/完整替换/调 query） | 403 |
| ② 提示词窃取专项 | B 通过 update / deleteId / activeId / 完整替换列表 / `/api/query` 引用 A 的 prompt_id | 403 |
| ③ 内容层 | B 的**响应文本**不含 A 的私有标记 `PRIV_A_xxx` | 不含标记 |
| ④ 并发层 | A、B 同时（线程池 8 并发）创建会话并读列表 | 零交集 |
| ⑤ 数据层 | 直查数据库：B 名下 prompts / messages / compare_history 中均无 A 的标记内容；对照 A 名下确有 | 计数为 0 / >0 |

## 二、测试方法

### 2.1 测试目标（对应需求原文）

> 测试数据库读写是否会读取其他人的隐私：多账户登录，同时尝试在提示词中输入其他用户的 id 尝试窃取其他用户隐私。

### 2.2 测试步骤设计

1. 注册并登录 A、B 两个账号；
2. A 创建带私有标记（`PRIV_A_xxx`）的资源：会话（含标记消息）、提示词、对比记录；
3. B 以自己合法的 token 尝试**所有可能的窃取路径**：
   - 用 A 的资源 id 直接操作（接口层）；
   - 在提示词中输入 A 的 prompt_id（update / deleteId / activeId / 完整替换列表 / query 引用）；
4. 断言 B 的任何响应**文本**不含 A 的标记（内容层）；
5. A、B 并发操作，验证列表零交集（并发层）；
6. 直查数据库，验证 B 名下数据行中无 A 的标记（数据层）；
7. 清理测试账号。

### 2.3 用例矩阵（25 项断言）

| 分组 | 用例 | 断言 |
|---|---|---|
| A 创建资源（3） | 创建会话并写入标记消息 / 创建标记提示词 / 创建标记对比记录 | 200 |
| ① 接口层（6） | B 读 A 会话消息 / 改名 A 会话 / 删除 A 会话 / 删除 A 对比记录 / 用 A 的 session_id 调 query / 用 A 的 prompt_id 调 query | 403 |
| ② 提示词窃取（4） | B update A 提示词 / delete A 提示词 / 激活 A 提示词 / 完整替换列表含 A 的 id | 403 |
| ③ 内容层（5） | B 的提示词库 / 会话列表 / 对比历史响应不含 `PRIV_A_xxx`；对照：A 的提示词库含标记、A 能读自己的会话含标记 | 不含 / 含 |
| ④ 并发层（3） | 8 路并发创建会话全部 200 / A、B 会话列表零交集 / B 的列表不含 A 的标记会话 | 零交集 |
| ⑤ 数据层（4） | B 的 prompts / messages / compare_history 中无 A 标记；对照：A 的 prompts 确有标记 | 0 / >0 |
| **合计** | **25** | 3+6+4+5+3+4 = 25 |

## 五、结论

1. **数据隔离验证通过**：接口层、提示词窃取专项、内容层、并发层、数据层五类断言 **25/25 全部通过**；
2. 关键结论：B 用合法身份尝试全部窃取路径均被拒绝（403），且**任何响应内容中都不存在 A 的私有标记**——不存在"能访问但泄露内容"的半隔离；
3. 数据库层验证：B 名下数据行中无 A 的任何标记内容，数据物理隔离成立；
4. 测试账号自动清理，未污染业务数据。

## 六、遗留建议

| 项 | 建议 |
|---|---|
| 多轮对话历史隔离 | 前端 `/api/query` 的多轮 `messages` 由客户端传入，服务端信任其角色归属；建议补充测试点 5：验证跨会话上下文不会串入他人历史（服务端应以 session_id 归属为准重建历史） |
| 并发压测 | 并发层当前仅覆盖"创建+读列表"；建议测试点 3 用 `scripts/concurrency_test.py` 做读写混合压测（含安全路径问题池） |
| 数据层深挖 | 可增加"删除他人数据后的级联影响"用例：验证 B 删除自己会话不会影响 A 的关联数据 |
| 生产加固 | 数据隔离依赖 `user_id` 归属列与查询过滤，建议数据库层补充索引（user_id 已建 index）与定期审计 SQL（扫 user_id 为空/异常行） |
