## 一、测试方法

### 1.1 目标（对齐「Mock · 系统自身上限」示例）

阶梯并发（1 → 10 → 50 → 100），每个并发级持续 6s，测量 3 个接口的请求数 / 失败数 / Avg / P95 / P99 / RPS：

| 接口 | 方法 | 语义 |
|---|---|---|
| `/api/system-prompt` | GET | 纯 DB 读（提示词隔离查询，最轻） |
| `/api/query` | POST | 完整同步 RAG：安全检测 + PGVector 检索 + mock 生成 + 落库 |
| `/api/query/stream` | POST（SSE） | 流式：TTFT（首 token 时延）+ 完整时延 |

### 1.2 环境说明

- **Mock 边界**：只替换外部依赖（embedding API / LLM），本地处理（FastAPI、PostgreSQL、pgvector、安全关键词、prompt 隔离）全走真实代码 → 测的是**系统自身上限**，不受外部网络与费用噪音影响；
- 压测脚本与 uvicorn **同进程**，mock 才能对服务生效；单 worker（与功能测试一致的单进程语义）；
- 用户池：10 个独立压测账号轮流使用（多用户真实场景）；
- 压测后自动清理压测账号与数据。

## 三、边界探测（`--boundary` 模式，2026-08-19）

> 阶梯模式（1/10/50/100）用于**找拐点**；边界模式按 1→2→4→…**倍增加压直到失败**，用于找系统上限。

### 3.1 运行方式

```bash
# 并发按 1→2→4→…→1024 倍增，每级 5s，测 /api/query
python tests/test_performance.py --boundary --duration 5 --report tests/results/performance-boundary.json

# 自定义上限与软边界阈值
python tests/test_performance.py --boundary --boundary-max 2048 --boundary-p99 8000
```

| 1 | 575 | 0 | 8.7ms | 11.1ms | 20.6ms | 115.0 |
| 2 | 835 | 0 | 12.0ms | 14.8ms | 19.6ms | 167.0 |
| 4 | 466 | 0 | 43.5ms | 144.2ms | 195.0ms | 93.2 |
| 8 | 157 | 0 | 259.3ms | 370.8ms | 487.5ms | 31.4 |
| 16 | 247 | 0 | 325.8ms | 578.0ms | 814.5ms | 49.4 |
| 32 | 798 | 0 | 204.5ms | 259.1ms | 282.3ms | 159.6 |
| 64 | 720 | 0 | 459.1ms | 749.8ms | 972.5ms | 144.0 |
| 128 | 769 | 0 | 877.8ms | 1918.4ms | 2770.9ms | 153.8 |

### 3.3 边界结论

| 指标 | 值 | 说明 |
|---|---|---|
| **硬边界（错误率 > 0）** | **512 并发**（208 失败，~21%） | 连接/事件循环/数据库连接池耗尽，首次出现失败 |
| **可接受上限（0 失败）** | **256 并发**（P99 5.3s） | 256 并发内全部成功 |
| **吞吐峰值** | ~195 RPS（512 并发） | 单进程 uvicorn 的吞吐天花板 |
| **早期波动** | 8/16 并发 avg 反而高（259/325ms） | 受首次预热影响（BM25 索引/连接池初始化），32 并发起稳定 |

> 结论：**单进程 Mock 环境下，系统的可靠服务上限约为 256 并发（0 失败、P99 < 6s），512 并发进入硬边界**。调优建议（HNSW 索引、prompt_store 锁、连接池）落地后可复测边界是否上移。

## 四、瓶颈归因

| 瓶颈 | 证据 | 说明 |
|---|---|---|
| **prompt_store 全局锁串行** | system-prompt 1→100 并发劣化 153×，最严重 | 每次 GET 都进 `_lock` 查 prompts 计数 + 可能 seed，全局锁使所有用户读取串行化 |
| **pgvector 无 HNSW 索引** | query 每请求检索 ~40ms 起步 | 迁移时 `add_embeddings` 后未建 HNSW/IVFFlat 索引，257×1024 全表扫描（数据小尚可，并发下放大） |
| **SQLAlchemy 连接池过小** | query/system-prompt 并发下延迟线性上升 | 默认 pool_size=5 + max_overflow=10，100 并发时连接排队 |
| **单 worker asyncio** | stream TTFT 100 并发 4.9s | SSE 长连接占用事件循环，单 uvicorn worker 是吞吐天花板 |
| **embedding LRU 未命中** | query 日志 embed 0ms（mock） | mock 后 embed 免费；真实环境 embedding API 是最大外部时延（300ms+），缓存命中率决定实际体验 |

---

## 五、结论

1. **正确性**：0 失败、100 并发稳定，无错误响应；
2. **单用户体验**：完整问答 ~40ms、流式 TTFT ~40ms（Mock 环境），满足交互式要求；
3. **系统上限**（Mock · 单进程）：问答吞吐 ~26 RPS、流式 ~20 RPS；**并发 ≥ 50 为延迟拐点**，100 并发 P99 达 5-7s；
4. **边界**（`--boundary` 探测）：硬边界 512 并发（首次失败）、可靠上限 256 并发；
5. **最大短板**：prompt_store 全局锁（system-prompt 读取串行化）+ 单 worker 事件循环（流式劣化最快）。

## 六、调优建议（按性价比排序）

| 优先级 | 优化项 | 预期收益 |
|---|---|---|
| P0 | pgvector 建 **HNSW 索引**（`vector_cosine_ops`） | 检索从全表扫描→log(n)，query 延迟与并发抗性显著提升 |
| P0 | **prompt_store 用户 seed 状态内存缓存**（首次 seed 后标记，GET 不再拿全局锁） | system-prompt 并发劣化 153× → 接近常数 |
| P1 | SQLAlchemy 连接池调大（`pool_size=20, max_overflow=40`） | 100 并发连接排队缓解 |
| P1 | 多 worker 部署（uvicorn `--workers N`）+ Redis 共享限流/缓存 | 吞吐 ×N（需配套共享存储，见并发安全报告遗留项） |
| P2 | embedding LRU 扩容 / 检索向量本地缓存 | 真实环境 embedding 300ms+ 是最大时延，命中率决定体验 |
| P2 | 流式接口节流（并发上限 + 背压） | 防止 SSE 长连接耗尽事件循环 |

> 注：本报告为 **Mock 环境**（embedding/LLM 替身）下的**系统自身上限**；**真实链路（真实 LLM 调用）的并发压测见测试点 5《真实链路压测测试报告》**——真实环境吞吐上限由模型提供方 QPS 决定。
