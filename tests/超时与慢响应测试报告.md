## 一、为什么要测超时与慢响应

### 1.1 上游抽风是常态

LLM 提供方（DeepSeek/通义）随时可能：
- **挂起**：请求发出后无任何响应（60s+）；
- **变慢**：响应慢但持续输出；
- **限流/5xx**：瞬时错误。

系统必须有明确行为：**不无限挂起、不拖垮其他用户、失败可恢复**。

### 1.2 本系统当前的防护机制（被验证的对象）

| 机制 | 当前配置 | 说明 |
|---|---|---|
| httpx 超时 | `timeout=30s`（连接/读取） | 上游 30s 无响应 → 主动放弃 |
| SDK 重试 | `max_retries=2` | 连接错误/超时/429/5xx 自动重试 |
| 线程隔离 | FastAPI `run_in_threadpool`（40 线程） | LLM 同步调用不阻塞事件循环 |
| 兜底 | 500 + "内部处理失败，请稍后重试。" | 异常不外泄内部细节 |

> 测试用 8s 超时加速验证机制（默认 30s 同机制，跑满太慢）。

## 二、测试方法

### 2.1 mock 方案（关键设计）

测试进程内起 ThreadingHTTPServer 模拟 LLM API，**按模式分服务器**（openai SDK 请求路径固定）：

| 模式 | 行为 | 验证点 |
|---|---|---|
| `slow` | 每次请求挂起 60s（无响应字节） | ① 超时主动放弃 + 兜底 |
| `flaky` | 首次挂起 60s，重试时立即成功 | ② SDK 自动重试 |
| `fast` | 立即返回 | ④ 链路正常 |
| `slow15` | 挂起 15s 后正常返回（< 超时 30s） | ③ 并发慢请求 |

ChatOpenAI 指向 mock 服务器（`base_url=http://127.0.0.1:<port>/v1`），**真实走 httpx read-timeout 与 SDK 重试**——不是 patch 方法返回值，而是端到端验证网络层行为。

### 2.2 用例（9 项断言）

| 用例 | 断言 |
|---|---|
| ① 慢响应（挂起 60s > 超时 8s） | 请求在 ~16s（8s×2 次尝试）内主动放弃（<30s）；返回 500 兜底；兜底文案含「稍后重试」 |
| ② 首次超时后重试 | 重试后 200；回答来自重试成功（RETRY-OK）；总耗时 ≈ 8s 超时 + 重试 |
| ③ 并发慢请求（8 路，各挂 15s） | 8 个全部 200；总耗时 <40s（并发而非 8×15s=120s 串行） |
| ④ 恢复正常 LLM | /api/query 正常返回 200 |

## 三、测试结果（2026-08-21，9/9 通过）

### 3.1 运行输出（关键行）

```text

  [PASS] 返回 500 兜底（未崩溃、未挂死）
  [PASS] 兜底文案存在（含『稍后重试』）

== ② 首次超时后 SDK 自动重试 → 最终成功 ==
  [PASS] 重试后返回 200
  [PASS] 回答来自重试成功（RETRY-OK）        llm: 8517ms（≈ 8s 超时 + 重试成功）
  [PASS] 总耗时 ≈ 首次超时(8s) + 重试成功（<20s）

== ③ 并发：8 个慢请求并发处理，不串行阻塞、不拖垮 ==
  [PASS] 8 个慢请求全部完成（200）          各 llm: 15006ms
  [PASS] 并发完成而非串行阻塞（总耗时 < 40s，8×15s 串行=120s）

  [PASS] 恢复后 /api/query 正常返回（200）  llm: 1171ms
```

### 3.2 结果解读

| 验证点 | 结论 |
|---|---|
| **① 超时主动放弃** | ✅ 上游挂起 60s > 超时 8s → 请求在 ~16s 内主动放弃（httpx read-timeout 真实生效），不无限挂起 |
| **② 兜底** | ✅ 返回 500 + "内部处理失败，请稍后重试。"——异常不外泄内部细节，用户得到明确反馈 |
| **③ 重试** | ✅ SDK `max_retries` 自动重试：首次超时（8s）→ 重试 → 成功（8.5s 返回 RETRY-OK） |
| **④ 不拖垮线程池** | ✅ 8 个慢请求并发处理（15s 完成 vs 串行 120s）——`run_in_threadpool` 架构下慢请求互不阻塞，事件循环不被占用 |
| **⑤ 恢复能力** | ✅ 上游恢复后，链路立即正常工作（1.2s 返回） |

## 四、发现与结论

1. **超时机制真实有效**：httpx read-timeout 在"上游完全挂起"场景下正确触发，请求主动放弃而非挂死（生产默认 30s，测试用 8s 验证同机制）；
2. **重试闭环正常**：SDK 自动重试（首次超时 → 重试成功），用户无感；
3. **架构健康**：`async def + run_in_threadpool` 使慢 LLM 请求占用线程池而非事件循环，8 路慢请求并发互不拖累；
4. **兜底存在但可更友好**：当前是**通用 500 文案**"内部处理失败，请稍后重试。"——有兜底、不泄露细节，但**未区分 LLM 超时/上游故障**与真正的内部 bug。建议优化（见下）。

## 五、遗留建议

| 优先级 | 建议 | 说明 |
|---|---|---|
| P1 | **LLM 超时专用兜底**：捕获 `APITimeoutError`/`APIConnectionError` 返回 503 + "网络不佳，请稍后再试" | 与内部 500 区分，前端可针对性提示重试；心理场景尤其需要温和措辞 |
| P2 | 流式接口（/api/query/stream）超时同样验证 | 本测试聚焦同步 /api/query；流式长连接的 read-timeout 行为可后续补充 |
| P2 | 线程池水位监控 | 40 线程池被慢请求占满时新请求排队；可加指标（排队长度）与告警 |
| P3 | 慢请求降级（可选） | 超时后自动降级为"无检索纯模型回答"或缓存兜底，避免完全失败 |
